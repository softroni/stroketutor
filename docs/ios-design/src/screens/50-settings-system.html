Developer notes

Purpose

§29“Minimal; speed/accessibility/privacy/reset where useful.” Settings is not a feature surface. Every row here either changes how a lesson plays, makes the app readable, or answers a question about privacy. Nothing on this screen creates an obligation.

Layout

  • Inset-grouped list, 20 pt gutters, section headers in 13 pt uppercase at 55% ink. Rows are ≥ 60 pt (Theme.minimumTapTarget).
  • Large navigation title “Settings”, inline on scroll (standard .navigationBarTitleDisplayMode(.large)).
  • Playback speed is a segmented control inside its row, not a push — three values do not deserve a second screen.
  • “Reset progress” sits in its own group at the very bottom, red label, no icon, no chevron — the iOS convention for a destructive row.
  • Version line is 13 pt at 35% ink, centred, below the last group.

States & interactions

  • Narration row shows On / Off from the same key the player reads, so the two can never disagree.
  • Practice reminder row shows Off, or the schedule in words: “Weekdays 7:30”, “Mon, Thu 20:00”, “Every day 7:30”. Never a raw date.
  • “Replay the introduction” pushes nothing — it presents onboarding as a full-screen cover from ob-1 and sets hasSeenOnboarding = false only after the learner finishes it, so a cancelled replay does not re-arm first-run.
  • “Reset progress” → confirmation alert, see st-system variant reset.

Developer notes

Purpose

Narration is the one genuinely new thing in this design, so it gets one screen that explains itself. Two decisions a learner cares about are surfaced as read-only rows rather than buried in a privacy policy: what happens to their music, and whether silent means silent.

Layout

  • Toggle row first — a settings screen answers its own title in the first 60 pt.
  • The sample card is the only interactive demo. Play button is a 48 pt circular secondary; the .narration chip animates while the file plays and returns to rest when it finishes.
  • The “Voice” row is visually future-marked (45% opacity, non-interactive) rather than hidden, so the shape of the screen does not change when a second voice ships. Ship it hidden if the creator would rather not promise it — one if voices.count > 1.

Audio behaviour — the decision

Duck, do not pause — and stay under the silent switch. Session category .ambient with options [.duckOthers, .interruptSpokenAudioAndMixWithOthers], activated when a step begins narrating and deactivated with .notifyOthersOnDeactivation when the lesson ends.

  • Why duck: a lesson is a four-minute sequence of 2–3 second clips with long silences while the learner draws. Pausing music would stop and restart it five times in one lesson, which is worse than a short dip. Ducking is also what a navigation app does, and this is the same shape of interruption: short spoken guidance over a continuous background.
  • Spoken audio is different. Ducking a podcast just makes it unintelligible under a voice, so .interruptSpokenAudioAndMixWithOthers pauses spoken-audio apps and resumes them on deactivation. Music ducks; podcasts pause.
  • Calls: never interrupt. An AVAudioSession.interruptionNotification with .began stops narration and leaves the animation running — the written instruction is still on screen, so the lesson is not blocked.
  • Silent switch: honoured, and that is what picks the category. .playback deliberately ignores the ring/silent switch, which is right for a music app and wrong here — a learner who silenced their phone in a waiting room did not consent to a voice. .ambient obeys the switch and stops when the screen locks, and both are correct for this app: a locked screen means nobody is watching the step. The row on screen promises exactly this, so do not quietly change the category later.

The voice asset pipeline

  1. The creator writes or edits a step instruction in the Studio.
  2. The Studio calls ElevenLabs with that instruction and the chosen voice, and writes the result to shared/Assets/Voice/<lessonId>/<stepId>.m4a, alongside a voice.json manifest recording the voice id, model, and a hash of the instruction text.
  3. The step's voiceover field (already reserved in tutorial.schema.json v1) carries the bare file name — never a path, for the same reason reference photos are bare names: a relative path can point outside the folder.
  4. A changed instruction changes the hash, and the Studio marks that clip stale and offers to regenerate. Nothing regenerates silently: audio costs money and a re-render of an unchanged line wastes it.
  5. Assets/Voice/ ships as a folder reference in the Xcode project, exactly like Tutorials/, so adding a lesson's audio needs no project change.

The app tolerates a missing file. Bundle.main.url(forResource:) returning nil is not an error: the step plays silently, the narration chip does not appear for that step, and a one-line warning joins PreparedTutorial.warnings (the same array TutorialLoader already fills for clamped durations). Never block a step on audio — the learner has a pen in their hand.

Data

  • settings.narrationEnabled (Bool, default true) — the single source of truth, written from here and from the player's chip.
  • Sample clip: the first step of simple-house. If that file is missing, hide the whole sample card rather than showing a dead button.
  • Transcript line = the same step.instruction string that feeds the clip, read from the tutorial, not duplicated in code.

Accessibility

  • VoiceOver and narration must not talk over each other: when UIAccessibility.isVoiceOverRunning, do not auto-play narration at step start; the chip becomes an explicit “Play narration” button.
  • Toggle label “Lina talks you through each step”, value “On”/“Off”, hint “Turns the spoken instructions on or off. The written instruction stays.”
  • The sample's wave animation is decorative: .accessibilityHidden(true), and it does not animate under Reduce Motion (the chip just shows a static level).

Developer notes

Purpose

§31 names the audience obligation directly: readable type, generous targets, high contrast, Dynamic Type, minimal hidden gestures, reduced motion for non-drawing motion while preserving the essential tutorial animation in a sensible form. This screen is where those become switches, and where the “sensible form” is defined.

Reduce motion — what “sensible form” means

  • Default state follows UIAccessibility.isReduceMotionEnabled; the toggle shown here is an in-app override, so a learner who wants the whole system animated can still calm down this one app. Store as settings.reduceMotionOverride (Bool, default false) and treat the effective value as system || override — the override can only ever reduce motion, never force it back on against a system preference.
  • Reduced form of a step: each stroke appears at full length with a 180 ms cross-fade, in order, honouring the stroke's own duration as the delay before the next one. The learner still sees which line comes next and in what order, which is the entire teaching content; only the travelling pencil tip and the dash-offset sweep are dropped.
  • The pencil-tip dot is removed entirely under reduce motion (it is pure motion) and .stroke.draws collapses to a near-zero duration, which the design system already does at prefers-reduced-motion.
  • Everything non-drawing — screen pushes, the completion reveal, the narration wave — uses .animation(nil) or a cross-fade.

Left-handed layout

  • Mirrors two things only: the persistent reference thumbnail moves from the leading corner of the canvas to the trailing one, and the quiet control row (Back · Replay · Speed) swaps ends with the primary button's alignment.
  • Why: the phone sits beside the paper and the learner reaches across it with the hand holding the pen. That arm sweeps over one half of the screen on every “I drew it”. The reference has to be outside the sweep; the controls should be inside it. Mirroring is the only way to serve both hands with one layout.
  • Implement as an environment value, not as scattered ifs: \.layoutDirection is wrong (it would mirror text too). Add @Environment(\.handedness) with .right/.left and use it to pick .topLeading/.topTrailing and an HStack ordering. Text, chevrons and back buttons must not flip.
  • The iPad landscape player mirrors the whole reference/canvas split the same way.

High contrast paper

  • Swaps Theme.paper #FAF7F0 → #FFFFFF and ink #2B2B2B → #0B0B0B, and multiplies every stroke's lineWidth by 1.25 with a floor of 10 pt. Contrast goes from about 11.9:1 to 19:1.
  • It must also switch on automatically when UIAccessibility.isDarkerSystemColorsEnabled is true (Increase Contrast), with the same override rule as reduce motion.
  • A tutorial's own style.strokeColor is respected unless high contrast is on, in which case it is darkened toward #0B0B0B — a lesson author cannot opt a learner out of contrast.
  • Faded earlier steps go from 28% to 45% opacity, or they vanish on a white page.

Dynamic Type — what must reflow

  • Support to .accessibility5. Nothing uses .minimumScaleFactor in body copy; shrinking text for an older adult defeats the purpose.
  • Above .accessibility1: list rows become VStacks (label over value), the icon wells are dropped, the segmented speed picker becomes a Menu, and the tab bar grows to fit its labels — do not let it truncate to “Sketch…”.
  • In the player the order of yielding is fixed: canvas height first, then the reference thumbnail becomes a full-width row above the canvas, then secondary controls stack. The instruction card and the 68 pt primary button never shrink.
  • Guard rail: an Xcode preview at .accessibility5 for every screen, and a snapshot test for the player at .accessibility3.

VoiceOver

  • The canvas is one element: label “Drawing in progress, step 2 of 5”, value = the step instruction. It is not a container to explore stroke by stroke — that is noise.
  • Post .announcement when a step finishes drawing: “Step drawn. Ready when you are.” This replaces the visual cue that the animation has stopped.
  • Every toggle here has an explicit hint sentence; the previews are .accessibilityHidden(true) with a text alternative directly beneath, which is what the captions on screen already are.

“Paper Couch” Would Like to Send You Notifications

Notifications may include alerts and sounds. These can be configured in Settings.

Asking permission shows both halves: our own primer, which can be declined with no cost, and the system prompt that follows only after “Choose a time”. The one-shot system prompt is never spent on a learner who has not already said yes.

Developer notes

Purpose

§30 forbids “pressure-heavy daily streak mechanics”. A reminder is still useful for an adult with limited time, so the compromise is: opt-in, learner-scheduled, single, and explicitly consequence-free. The copy says so on the screen, not only in a footnote — “Nothing is counted” is the promise the whole feature rests on.

Layout & interactions

  • Toggle row first; everything below it appears only when it is on, animated with a section insert (cross-fade under reduce motion).
  • Days are seven 44 pt circles, multi-select, at least one required — turning off the last day turns the whole reminder off rather than leaving an impossible schedule.
  • Time is a standard DatePicker(.hourAndMinute) in wheel style; the mock shows it inline because a push for one value is a wasted screen.
  • The notification preview is a real preview of the real string. If the copy changes, this changes.
  • Flipping the toggle on goes to the primer, not straight to the system prompt. Declining the primer leaves the toggle off and nothing is requested, so the learner can change their mind later.

Notifications

let center = UNUserNotificationCenter.current()

// 1. only after the learner tapped "Choose a time"
let granted = try await center.requestAuthorization(options: [.alert, .sound])

// 2. schedule one repeating request per selected weekday
func reschedule(weekdays: [Int], hour: Int, minute: Int) async {
  center.removePendingNotificationRequests(withIdentifiers: Self.allReminderIDs)
  guard reminderEnabled, await isAuthorized() else { return }
  for weekday in weekdays {                      // 1 = Sunday … 7 = Saturday
    var components = DateComponents()
    components.weekday = weekday
    components.hour = hour; components.minute = minute
    let content = UNMutableNotificationContent()
    content.title = "A few quiet minutes with a pen?"
    content.body  = nextLessonTeaser()           // "Your next house is ready."
    content.sound = .default
    let request = UNNotificationRequest(
      identifier: "reminder.weekday.\(weekday)",
      content: content,
      trigger: UNCalendarNotificationTrigger(dateMatching: components, repeats: true))
    try? await center.add(request)
  }
}
  • Cancel on toggle off: removePendingNotificationRequests for all seven ids, every time. Never leave an orphan request — a notification arriving after the learner turned reminders off is the exact betrayal this design is avoiding.
  • Re-schedule on every change of days or time, and once at launch, because a learner may have revoked permission in iOS Settings since.
  • If getNotificationSettings() reports .denied while the toggle is on, show an inline row “Notifications are off for Paper Couch · Open Settings” and turn the toggle off. Do not re-request; iOS only asks once.
  • No badge. .badge is not in the options list: a red dot counting unfinished lessons is a streak by another name.
  • nextLessonTeaser() reads the next unlocked lesson from the progress store and produces “Your next house is ready.” / “Your next tree is ready.” from the path title, not the lesson title — a notification should not spoil the subject. If nothing is next (all paths complete), use “Your sketchbook is waiting.”

Data

  • settings.reminderEnabled Bool, default false. settings.reminderWeekdays [Int] as JSON, default [2,3,4,5,6] (Mon–Fri). settings.reminderHour 7, settings.reminderMinute 30.
  • The Settings row's value string is formatted from these: “Off”, “Weekdays 7:30”, “Every day 7:30”, “Mon, Thu 20:00”. Use Date.FormatStyle so 7:30 and 07:30 follow the locale.
  • Nothing about the reminder is written to the progress store, and no “last opened” date is ever recorded. There is deliberately no data from which a streak could later be computed.

Accessibility

  • Day circles: label the full weekday name (“Monday”), not “M”; value “selected” / “not selected”; trait .isButton. Group them with .accessibilityElement(children: .contain) and the label “Days”.
  • The preview banner is one element read as “Notification preview. A few quiet minutes with a pen? Your next house is ready.”
  • At accessibility text sizes the seven circles wrap to two rows rather than shrinking below 44 pt.

Open questions

  • Should the reminder also be offered at the end of the first lesson, where motivation is highest? That is the effective moment, but it is also the moment a learner is least able to judge. Recommendation: offer it once in onboarding (ob-voice mentions “an optional gentle reminder”) and never again unprompted.
  • Time-sensitive or not? Recommendation: no interruption level above .active. A drawing reminder that breaks through Focus is not calm.

Developer notes

Purpose

Three jobs in one stack: say what the app is in two sentences; discharge the attribution obligations of every bundled photograph; and answer “what happens to my drawings” without a lawyer's paragraph. §32 (“Store locally and privately by default”) is the whole privacy page.

Photo credits — where the list comes from

Each row is one lesson that has a reference in shared/Catalog/lessons.json:

{ "id": "palm-tree-4", "reference": { "file": "palm-tree-4.svg",
                                      "source": "pixabay", "license": "Free" } }

Grouping is by path: read Catalog/paths.json, walk lessonIds in order, emit a section per path and a row per lesson. A lesson with no reference still gets a row reading “Drawn from scratch · no photograph”, so the list is a complete audit of what shipped rather than a filtered highlight.

Recommendation: read the bundled catalog at runtime, not a generated file.

  • Catalog/ already has to be in the bundle for paths, unlock order and objectives; the credits list is three fields off an object that is in memory anyway.
  • A build-time script produces a second artefact that can silently drift from the catalog — exactly the failure mode that makes an attribution list a legal problem instead of a screen. One source, one truth.
  • It also means adding a lesson in the Studio updates the credits with no code change, which is the same property that makes Tutorials/ a folder reference.

What the build should do instead is fail: add a check to the release script (and a unit test) asserting that every lesson with a reference has a non-empty source and license, and that Assets/References/<file> exists. The Studio validates this already; the app-side test is the backstop for a hand-edited catalog.

  • source today is a bare slug ("pixabay"). Map it through a small display table — pixabay → “Pixabay”, unsplash → “Unsplash” — and fall back to the raw string rather than hiding an unknown source.
  • license today is free text ("Free"). It should become an enumeration in the Studio before launch, because “Free” is not a licence name; “Pixabay Content License” is. Flagged as an open question.
  • Add an optional author to reference: CC BY and CC BY-SA require attributing the photographer, and there is nowhere to put a name today. The mock's third Houses row shows what that looks like.
  • The thumbnail is the bundled reference asset itself, drawn at 44 pt. In the mockup those are .photo placeholders — no licensed images live in this document.

Decisions the creator owns, not the engineer:

  • Analytics at all? “No analytics by default” is written above. The honest options are none, or a strictly local, opt-in, aggregate-only counter that is never transmitted. Anything else means rewriting this page and filling in App Privacy — and an analytics SDK is the first thing that would break the “no network connection” claim.
  • Crash reporting counts as analytics to a reader, even though Apple's own crash reports are opt-in at the OS level and collect nothing for us. Recommendation: rely on Xcode Organizer only, and say nothing, because nothing is collected by us.
  • iCloud backup of the sketchbook. Included in the device backup by default, which most people want and which contradicts nothing on this page — but “stays on this device” is then approximately, not literally, true. Recommendation: leave backup on and change the line to “Your drawings stay on this iPhone and in your own iPhone backup.”
  • Contact address. hello@papercoach.app is a placeholder; App Store review requires a real, monitored one.
  • Privacy policy URL. The App Store listing requires a hosted policy even when the app collects nothing. That URL is the one piece of this that cannot live only in the app — and opening it is the one thing on this screen that needs the network, which is why it is a listing link rather than a row here.

Developer notes

Reset progress

  • .confirmationDialog is wrong here — a destructive action with a consequence that needs a sentence of explanation belongs in an .alert, where the message is readable. Title “Reset progress?”, message as shown, Button("Reset", role: .destructive) and Button("Cancel", role: .cancel).
  • What it clears: the progress store only — completed lesson ids, current lesson per path, and last-played timestamps. One call, ProgressStore.resetAll(), which removes its own file and re-publishes an empty value; do not iterate UserDefaults keys.
  • What it never touches: the sketchbook (photos and their lesson/path/date metadata), and every settings.* key. The alert message promises the first explicitly. A learner who resets progress to start the Houses path again has not asked to lose eleven photographs of their own drawings.
  • Deleting sketchbook entries is a separate, per-entry action on sk-entry. There is deliberately no “delete everything” button anywhere in Settings.
  • After reset, pop to the root of the Learn tab so the learner is not left looking at a path detail that no longer describes their state.

Content problem — the lenient loader, seen from the learner's side

shared/README.md records the divergence deliberately: the device is lenient because it must never strand a learner mid-lesson, and the Studio is strict because catching a bad export before it ships is the tool's entire job. Three behaviours follow, and all three are already implemented in TutorialLoader:

ProblemLoaderWhat the learner sees
duration or lineWidth of 0clamps to 0.8 s / 8, appends a warningnothing — the lesson plays
unknown property, bad hexignores / falls back to the default colournothing
unparseable path, missing fieldthrows; the file becomes a TutorialLoadFailurethe lesson is simply not in the list
schemaVersion 2isForNewerApp → continue, not even recorded as a failurenothing
  • The path screen filters, it does not apologise. Build the lesson list from paths.json, drop every id that did not produce a PreparedTutorial, and number the rows by their position in the filtered list. A gap in the numbers is a bug report the learner cannot act on.
  • Lesson counts (“9 lessons”), progress fractions and path-complete detection all use the filtered list, so a path with a skipped lesson still reaches 100%.
  • The Problems view must not ship visible. Today ContentView shows failureBanner and the full-screen TutorialProblemsView unconditionally. In M7 both move behind #if DEBUG — keep the type, keep the tests, and add an entry point from a debug-only settings row. In release, a failure is written to os_log at .error and nowhere else.
  • Ship-blocking guard: a unit test that loads every file in Tutorials/ and fails if any produces a TutorialLoadFailure that is not isForNewerApp. A lesson silently missing from a release is a content bug that must fail CI, not fail quietly on a learner's phone.

Offline — the decision

There is no offline state in version 1, because there is no online state. The app makes no network request: lessons, catalog, reference photos and voice clips are all bundled. So there is deliberately no reachability check, no spinner, no “no connection” banner, no retry — every one of those would be a lie about how the app works, and each is a surface that can fail.

  • The only honest place to say it is About, as one positive sentence (“No network needed”) rather than an error state. That line is shown here promoted into a card; in the shipping About it sits where the about variant of st-about puts it.
  • Do not link Network.framework and do not add NSAppTransportSecurity exceptions. If a future build needs neither, reviewers and researchers can both verify the claim.
  • This stops being true the day remote downloadable content §39 ships. At that point the first real offline state appears — and it should still be quiet: bundled lessons keep working, and only the “more lessons” surface shows a connection message.
  • One near-miss: the App Store privacy policy link and any mailto: leave the app. Those are the system's problem, not ours, and neither needs a network state inside Paper Couch.

Camera denied

  • Reached from sk-capture when AVCaptureDevice.authorizationStatus(for: .video) is .denied or .restricted. Never present the camera UI first and fail into a black frame.
  • “Open Settings” = UIApplication.shared.open(URL(string: UIApplication.openSettingsURLString)!). It lands on Paper Couch's own settings page, where the Camera switch is.
  • “Choose an existing photo” uses PhotosPicker, which needs no permission at all under PHPickerViewController's out-of-process model — so it is a genuine way out, not a second dead end. Keep it even when the camera is available.
  • Info.plist strings, written as the learner will read them mid-lesson: 
    NSCameraUsageDescription
  "Paper Couch uses the camera to photograph your finished drawing
   so it can go into your sketchbook on this iPhone."

NSPhotoLibraryAddUsageDescription
  "Saves a copy of your finished drawing to your photo library when
   you turn on 'Also save to Photos'."
    NSPhotoLibraryUsageDescription (read access) is not needed: PhotosPicker does not require it, and asking for library read access in an app that promises nothing leaves the device is a bad trade.
  • If “Also save to Photos” is on and add-access is denied, save to the sketchbook anyway and show a one-line toast: “Saved to your sketchbook. Photos access is off.” Never lose the photograph.

No lessons — the state that should never ship

  • Triggered when the catalog resolves to zero playable lessons: an empty paths.json, a missing Catalog/ folder, or every tutorial failing to load.
  • Tone: state the fact, remove the blame, offer the one thing that might help. No error code, no “contact support” on a screen the learner cannot act on, and no exclamation mark.
  • The tab bar stays — the Sketchbook and Settings still work, and hiding navigation would make a content bug look like a broken app.
  • Guard rails so it never appears: a release-script check that paths.json is non-empty and every listed lesson resolves; the loader test above; and an assertion in #if DEBUG at launch. This screen exists so that if all three fail, the learner still sees a sentence instead of a blank tab.

Accessibility

  • The reset alert is announced with its message; the destructive role gives VoiceOver the right verb. Do not add a hint that repeats the message.
  • Camera-denied screen: focus moves to the headline on appear (.accessibilityFocused), so a VoiceOver user hears why they are here before the buttons.

Open questions

  • Should “Reset progress” also offer a second, explicit “Delete my sketchbook” inside the same alert? Recommendation: no. Two destructive actions in one dialog is how people lose photographs.
  • Is the debug Problems view worth an in-app entry point in TestFlight builds, not just DEBUG? The creator will be the main TestFlight user, and a bad export found on device is cheaper than one found by a learner.
